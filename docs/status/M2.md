# M2: Staged collector
Machine: Ryzen 7 5700X desktop (8 cores / 16 threads, Windows 11 Home build 26300.10075, bare metal, rustc 1.99.1)   Date: 2026-11-23

**The collector receives UDP and writes JSON lines, and nothing it reads is
lost without being counted.** One part of R3 is open on Windows: the OS
gives no count of datagrams dropped at a full socket buffer, so that loss is
seen only as sequence gaps. R5 is measured on loopback: about 960,000
records/s with no loss, and loss from 1.2 million records/s up.

## Built

- **`flowlanes-pipe`**, the staged collector on `stagelanes-pipe`
  (`stagelanes` `main` at `3f27631`, path dependency):

  ```
  socket -> receive -> decode -> encode -> output -> sink
               ^ blocks |          ^ buffers |
               +--------+          +---------+
  ```

  - Four stages, one thread each, pinned to logical CPUs 2, 4, 6 and 8 on
    this machine (`CorePlan::for_socket`, first core left to the OS),
    joined by `link`s.
  - receive reads each datagram into a 64 KiB block from a `BlockPool`
    (256 blocks, locked in memory) and stamps the time of receipt.
  - decode owns the template state (`flowlanes_wire::Collector`).
  - encode writes the JSON lines into reused buffers.
  - output hands them to a `Sink`, flushes, and records the time from
    receipt to flush for every record.
  - A full link makes the sender wait. The pipeline never drops anything
    itself; when it cannot keep up, the pool runs dry, receive stops
    reading, and the kernel drops at the socket.
  - Counters: datagrams and bytes read, read errors, waits for a free
    block, the decoder's counters, records written, records the sink
    refused, and the latency histogram. `Snapshot::balanced()` is the R3
    identity from socket to sink.
  - Configuration, none of it constants in the stages: listen address,
    `SO_RCVBUF` request (8 MiB asked and granted here), pool size, decoder
    limits, pinning, priority, and what an idle stage does (`backoff`,
    the default: 2,000 polls, then 1 ms sleeps; or `spin`).
- **`flowlanes collect`**: listens on `0.0.0.0:2055` by default, appends
  `flow` events to `--out FILE` or stdout, prints counters as JSON on
  stderr every `--stats-secs` and at the end, stops on Ctrl-C or
  `--duration`. Exits non-zero if the final counters do not balance.
- **Template timeout** in `flowlanes-wire` (left by M1):
  `Config::template_timeout_secs`, `--template-timeout`. A template not
  re-sent in time is discarded and counted (`templates_expired`); its data
  is then held like any data without a template. `flowlanes decode`
  disables it, because a packet file has no receive times.
- **`flowlanes-bench`**: generated IPFIX over loopback at rising rates;
  writes `runs/<machine>/<date>-collector[-n].json`.
- New dependencies: `socket2` 0.6.5 and `ctrlc` 3.5.3, both MIT OR
  Apache-2.0; every crate in `Cargo.lock` is MIT, Apache-2.0, Zlib,
  Unlicense-or-MIT or (one build-time crate) Unicode-3.0 with MIT OR
  Apache-2.0.

### R5 (run files in `runs/ryzen/`)

All four runs: commit `0366665`, release build, IPFIX datagrams of 1,364
bytes holding 24 IPv4 flow records, a template before every 20 data
packets, evenly spaced, 10 s measured after 2 s of warm-up per rate, nine
rates from 1,000 to 80,000 packets/s. Sender and collector are in one
process and the path is loopback, so no network card is involved. Quiet
system: nothing else building, no Actions runner process, Docker Desktop
not running, Balanced power plan.

Latency is per record, from the packet's scheduled send time to the flush
of its line (µs).

| Run file | Idle | Priority | Sink | Highest rate with no loss | p50 / p99 at 24,000 records/s | p50 / p99 at 960,000 records/s | max at 960,000 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `2026-11-23-collector.json` | backoff | normal | null | 960,000 records/s (40,000 packets/s) | 2,294 / 4,325 | 40 / 2,949 | 4,647 |
| `2026-11-23-collector-2.json` | spin | normal | null | 960,000 | 35 / 39 | 36 / 41 | 449 |
| `2026-11-23-collector-3.json` | spin | time-critical | null | 960,000 | 36 / 40 | 36 / 40 | 3,537 |
| `2026-11-23-collector-4.json` | backoff | normal | file | 960,000 | 2,228 / 3,867 | 55 / 11,534 | 16,066 |

- **No loss up to 960,000 records/s** in all four runs (40,000 packets/s,
  the last step below the limit; the next step tried was 1.2 million).
- **At 1.2 million records/s and above the collector loses data at the
  socket.** It wrote 12.4 to 12.5 million records in the 12 s of each
  overloaded step with the null sink, about 1.04 million records/s. Every
  lost record is in `sequence_missing`, and every step balances.
  The exact limit between 960,000 and 1.2 million was not searched for.
- **The encode stage is the limit** (inference from poll counts in a short
  trial run, not from a profile): it was the only stage with almost no
  idle polls when overloaded.
- **The default idle mode costs milliseconds at low rates.** With
  `backoff`, an idle stage sleeps 1 ms at a time, and a record takes about
  2 ms (p50) and 3.5 to 4.6 ms (p99) at 1,000 to 20,000 packets/s. With
  `spin` it takes 35 µs (p50) and 39 µs (p99) at every rate without loss,
  at the price of four cores kept busy.
- **Time-critical priority changed nothing measurable here**: p50 and p99
  match the normal-priority spin run. The worst single record was
  between 56 µs and 3.5 ms across the steps in both runs; the worst ones
  coincide with the sender itself running up to 2 ms late
  (`sender_max_lag_us`), which this latency includes.
- **Writing to a file** did not lower the no-loss rate, but p99 rose to
  27 ms at 720,000 records/s and 11.5 ms at 960,000.
- **Overloaded, a record takes about 172 ms** from send to flush, most of
  it waiting in the 8 MiB socket buffer; receipt to flush is about 29 ms.

These are loopback figures on Windows and are provisional, as CLAUDE.md
says of all Windows tail figures. They say nothing yet about a real
network card or about Linux.

## Deviations and corrections

- **R3, socket drops on Windows.** The spec asks for socket receive drops
  to be counted. Windows offers no per-socket count through safe code, and
  the system-wide counters do not show these drops either: 5,000 datagrams
  sent over loopback to a socket nobody read left `In Erroneous Datagrams`
  at 0 while `In Datagrams` rose by 5,000 (`netsh interface ipv4 show
  udpstats`, this machine, 2026-11-23). So on Windows the collector reports
  `socket_drops: null` with the reason, and the loss appears as
  `sequence_missing`. That cannot tell a socket drop from loss on the
  network, and it misses loss at the very end of a stream. SPEC R3
  annotated.
- **Four stages, not six.** SPEC §5 draws receive, decode, enrich,
  aggregate, detect, output. Enrich, aggregate and detect belong to M4. M2
  adds an encode stage between decode and output, because formatting JSON
  was the slowest step.
- **The stages do not keep the `stagelanes` stage rules** (no allocation,
  no lock, no system call after `ready`). receive and output make system
  calls by nature; decode allocates, because `flowlanes-wire` returns owned
  records; the counters are published under a mutex. Allocations per stage
  were not counted. Only the packet blocks and line buffers are pooled.
- **Default idle mode is `backoff`, not busy-polling**, so an idle collector
  does not hold four cores at 100%. It costs about 2 ms per record at low
  rates (measured above). `--idle spin` is the `stagelanes` behaviour.
- **Template timeout default, 1,800 s, is a placeholder.** Neither RFC gives
  a number. RFC 7011 §8.4 suggests at least 3 times the observed re-send
  interval; deriving it from observation is not built.
- **Per-exporter counters.** R3 says "per-exporter sequence gaps".
  Sequence numbers are tracked per exporter, but the counter reported is
  the sum over exporters, as in M1.
- **The exporter is the source IP address** of the datagram. RFC 7011 §8.4
  also lists the exporter's source port; two exporters behind one address
  would share template state.
- **JSON output moved**: `record_json` and `counters_json` now live in
  `flowlanes-pipe::json`. The counters gained `templates_expired`.
- **CLAUDE.md is out of date in two places**, corrected on this branch:
  the repo map said `stagelanes-pipe` was on a branch, and the commands
  lacked `collect`. It also says "agents never push; there is no remote
  yet"; this session pushed the branch and opened a pull request because
  the coordinating session's brief said to. Evan has since changed the rule
  (see Decisions).
- **`rust-version = "1.85"` in the workspace is not true**: `flowlanes-wire`
  has used `let` chains since M1, which need 1.88. Not changed here.
- The run-file date is the local date (2026-11-23); each file also records
  the UTC date and time.

## Open questions for Evan

1. **Firewall.** Receiving from the gateway needs an inbound rule. In an
   elevated PowerShell (not run by me; replace the address with the
   gateway's):

   ```
   New-NetFirewallRule -DisplayName "flowlanes IPFIX" -Direction Inbound -Protocol UDP -LocalPort 2055 -RemoteAddress <gateway address> -Action Allow
   ```

   The first start of `flowlanes collect` on `0.0.0.0` may also show the
   Windows firewall prompt. I only ever bound to `127.0.0.1`.
2. **Is "loss shows as sequence gaps" enough for R3 on Windows?** A real
   count would need ETW or an unsafe call, which this repo forbids. On the
   Linux machine the per-socket count is there, once someone runs it.
3. **Default idle mode.** `backoff` (about 2 ms per record, cores free) or
   `spin` (35 µs, four cores busy)? At home-network rates the delay does
   not matter to any detector planned; I kept `backoff`.
4. **Should counters also go into the output file** as their own event, so
   Wazuh can alert on loss? SPEC §5 names two event kinds, `flow` and
   `alert`; for now counters go to stderr only.
5. **Output file rotation** is not built. The file grows until the
   collector stops.
6. **Template timeout and hold limits** (1,800 s; 256 sets, 60 s) stay
   placeholders until the gateway's export is seen.
7. **Run on start-up?** Nothing installs the collector as a service or
   scheduled task.
